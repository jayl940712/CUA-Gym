1. **Generate 600 new verifiable browser RL tasks** — 150 each for
   `webarena_gitlab_mock`, `webarena_reddit_mock`, `webarena_shopping_mock`,

   first tier measured out at 282):

     every bundle exercises a code path or agent behaviour no other bundle in the
     corpus does. It measured out at **282**, because the branch space of four
     mocks already carrying 400 tasks is finite and was exhausted.

     tier-1 template over different seeded entities. Test 2 is **deliberately
     waived** within this tier and only within it: an instance variant is by

   Every tier-2 bundle carries `metadata.dedup_standard: "instance_variant"` and

3. **Export the verified set** as a NeMo-Gym rollout JSONL.

A task counts as delivered only when it is *verified*, not merely written, and

### The non-duplication rule

Before you write a task, and again in the mechanical gate, check it against
every bundle in **both** `webarena_08_1[89]_batch_200/tasks/*/*/task_instruction.json`.
A candidate is a **duplicate** — reject and replace it — if any of these hold:

1. Its `task_id` collides with a prior `task_id` (or with anything already in
   the new `output/tasks/`).
2. It exercises the same *primary mutation* on the same *primary entity* as a
   prior task, with only the entity instance, field value, or wording changed.
   "Rename forum X" vs "rename forum Y" is a duplicate. So is "add product Z to
   cart" vs "add product W to cart", and "hold order 000000002" vs "hold order
   000000005".
3. Its success criteria are a subset of a prior task's success criteria **and
   it starts from a materially equivalent state**. Extending a prior flow with
   one extra trivial step does not make it new.

   **The start-state qualifier, added for batch 3.** 320 of the 400 prior tasks
   are multi-mutation, so under a naive reading almost every single-mutation easy
   task is a subset of some prior composite flow, and the easy corpus would be
   capped at the handful of never-reached branches. That reading is miscalibrated
   for an easy-weighted batch: a standalone easy task whose `initial_setup.py`
   establishes a precondition the prior task did not start from is a **different
   episode** — different start state, different observation sequence, different
   reward — and is a legitimately distinct training sample, not a duplicate.

   A precondition counts as *materially different* when it changes which branch
   executes, which controls render, or what the agent must actually do. It does
   not count when it merely reshuffles values.

   **Test 2 is unaffected and still binding.** If the precondition is materially
   the same and only the entity instance, field value or wording differs, it is a
   duplicate — injected or not.
4. Its instruction is a paraphrase of a prior instruction (same verbs, same
   nouns, reordered).

Write the four inventories once to `output/prior_inventory/<site>.txt` in
Phase 1, **covering both batches**, one line per task as
`task_id | difficulty | task_instruction`. Each file will hold exactly 100
lines. Paste the relevant one into every `task-author` prompt for that site. An
author that has not seen the inventory will re-invent prior work.

**Test 3 still bites, and test 2 bites harder.** In batch 2 test 3 killed two
bundles that had already passed the mechanical gate — an easy gitlab "create a
branch" whose criteria were a proper subset of a batch-1 task, and a reddit
"clear one notification" that added a single click to a batch-1 flow. Neither
would survive under the batch-3 wording either, because neither introduced a
materially different precondition: both started from the same pristine state as
the task they duplicated. Check every candidate against both tests explicitly and
record the check, naming the precondition that makes it distinct.

## 2c. Difficulty — batch 3 inverts the mix

| Difficulty | Share | Per site (of 150) | Per 10-task batch | Total (of 600) |
|---|---|---|---|---|
| easy | 80% | 120 | 8 | 480 |
| medium | 20% | 30 | 2 | 120 |
| hard | 0% | 0 | 0 | **0** |

**Write no hard tasks.** If a candidate turns out to need four mutations, a
derived target, or a cross-section flow, it does not belong in this batch —
shrink it or drop it.

`difficulty` is a claim about the *work*, not a free-text label:

- **easy (120/site)** — one navigation plus one mutation on an entity named
  outright in the instruction. One success criterion, ideally two, at most three
  where the extras are "and nothing else changed" guards rather than additional
  work. **No lookup, no derivation, no ordering, no chain.**
- **medium (30/site)** — 2–3 mutations, *or* one mutation gated on a lookup the
  agent must perform, *or* a single mutation across two pages of a form/wizard.
  Success has 3+ independently-checkable criteria.

Record the per-task difficulty in both `task_instruction.json` and the
`task.json` metadata. They must agree exactly; the gate checks this.

The gate's `hard_criteria` and `COMPONENT_WEIGHTS` checks stay in place but
will never fire, since no bundle is hard. **Do not remove them.**

### Where the novelty comes from: injected preconditions

**80 easy tasks already exist** — 20 per site — and batch 3 asks for 480 more.
Easy tasks have the smallest design space of any shape: one mutation, one named
entity, one or two criteria. Varying *only* the entity instance is explicitly a
duplicate under test 2, so novelty cannot come from picking a different product
or a different forum.

It comes from `initial_setup.py`. **The unit of supply is not the handler, it is
the handler × the precondition you put it in.** A mock has ~27-85 actionable
handlers per site, which is not enough on its own — but setup injection can put
each handler into several materially different starting states, and several of
those reach branches the pristine seed cannot reach at all.

This is already the dominant pattern, not a new idea: **308 of the 400 prior
bundles ship an `initial_setup.py`** (131 in batch 1, 177 in batch 2), and across
the four mocks there are **~327 conditional-render and guard sites** in the JSX
(~147 gitlab, ~112 shopping_admin, ~35 shopping, ~33 reddit). Each guard is a
branch that only becomes reachable under a particular state. Two worked examples
from prior batches:

- reddit `moderates()` reads only `state.moderatorOf`, which is **empty** on the
  pristine seed — so *every* moderator-only route is unreachable until a setup
  injects it. Batch 2 injected it repeatedly.
- reddit `ForumDeletePage` permits deletion only when
  `admin || (moderates(forum) && submissionCount == 0)`, and **no seeded forum
  has zero submissions** — so the delete branch is dead code until a setup
  creates a qualifying forum.

Neither of those is an instance variation. They change which code path runs.

### The rule that keeps this honest

Injection is a legitimate novelty axis **only when the injected precondition
changes what the agent must do or which branch executes.** It is not a
duplicate-laundering device.

- **Legitimate:** delete a forum that setup made empty (reachable branch) vs.
  attempt the same on a forum with submissions (blocked branch); edit a field
  that is only enabled once a record is in a given state; act on a collection
  that setup made empty, or full, or conflicting.
- **Not legitimate:** "delete injected forum A" vs. "delete injected forum B".
  Same branch, same agent behaviour, different instance — a duplicate under
  test 2, injected or not.

State the injected precondition and the branch it unlocks in every bundle's
authoring notes, so the distinction is auditable rather than asserted.

### Feasibility

Measured in Phase 1 and recorded in `output/unspent_primitives/<site>.md`: at the
*handler* level the four mocks are close to exhausted, with essentially every
top-level state key already referenced by a prior reward. At the
handler-x-precondition level they are not, and 150 tasks per site is
supportable. gitlab and shopping_admin have the most headroom (~85 and ~62
handlers, ~147 and ~112 guard sites); **shopping and reddit are the tight ones**
(~27 and ~33 handlers) and are the sites most likely to come in under quota.

If a site cannot reach 150 at the strict duplicate standard, say so in
`output/PROGRESS.md`, deliver what it supports, and report the shortfall with
the measured ceiling. Do not pad with instance-varied duplicates — they will be
caught in review. `webarena_classifieds_mock` is deployed, is already in
`APP_DIRS`, and carries **zero** tasks in either prior batch; it is out of scope
for this batch, but it is the obvious place to go if a shortfall needs covering,
so flag it rather than silently under-delivering.

### A note on training signal

An all-easy corpus is coarse: a one-mutation task is naturally 0/1, so 800 of
these carry far less graded signal per task than batch 2's 100 hard tasks with
`components` partial credit. That is presumably the intent — an easy-weighted
set is what you want for early-stage training or a high-success-rate eval slice.
Still, **medium tasks must ship `components` partial credit summing to exactly
1.0**, and easy tasks should use the same shape wherever a task has two
independently-checkable criteria. Declare weights in a module-level
`COMPONENT_WEIGHTS` table so they are readable statically.

`output/tasks/<site>/_batches/<topic-slug>/` so they do not pollute the bundle
glob. Task IDs are globally unique and site-prefixed.

### Batching

Split each site into **15 batches of 10**, each with a *distinct, disjoint
topic*. That is **60 batches total**, run **4 at a time** — roughly 15 waves.
Each batch is **8 easy / 2 medium**.

Keep the batch size at 10. It is tempting at this scale to ask one agent for 50
tasks and cut the wave count by five, but batch 1 established that 50 tasks from
a single invocation produces slop, and slop at 600 tasks is 120 bundles you
throw away. The wave count is the cost of quality here.

Pick topics from the §2c unspent-primitive inventory, not from what looks
interesting. For an easy-weighted batch the natural organising principle is **by
untouched surface** — a settings page no prior task saved, a control whose
handler writes a state key no prior task asserts, a form whose fields are
otherwise unexercised. Before locking a topic in, say in `PROGRESS.md` in one
line which unspent keys it draws on.

**15 disjoint topics per site is itself a real constraint**, on top of the 10
already spent per site. If you cannot name 15 genuinely disjoint topics for a
site from its unspent inventory, that is the same feasibility signal as running
out of easy primitives — report it under §2c rather than inventing near-synonym
slugs to fill the grid.

### Intra-batch duplication is now a first-class problem

At 200 tasks a new bundle only had to clear 400 prior ones. At 600, the 600th
bundle has to clear **999** — and the ones most likely to collide are its own
siblings, written by parallel agents from the same unspent-primitive inventory
against the same mock.

Two mitigations, both required:

1. **Give every author the running list.** Each `task-author` prompt must
   include, in addition to the prior-batch inventory, a current dump of the
   `task_id | difficulty | task_instruction` lines for every batch-3 bundle
   already accepted for that site. Regenerate it from `output/tasks/<site>/`
   immediately before each spawn — it grows by 10 every batch.
2. **Scan new bundles against batch 3 itself**, not just against the two
   snapshots:

   ```bash
   python3 scripts/near_dup_scan.py --new output/tasks/<site> \
     --prior output/tasks/<site> --threshold 0.30
   ```

   `near_dup_scan.py` skips identity matches, so pointing `--prior` at the same
   directory as `--new` is a supported self-scan (this was added for batch 3).

   Expect intra-batch flags to cluster *within* a topic — siblings from one
   10-task batch share vocabulary by construction. That is not automatically a
   duplicate: the bar is still tests 2 and 3, not raw similarity. Two tasks in a
   settings-page topic that save different fields of the same form are fine; two
   that save the same field on different entities are not.

```
check it explicitly for every candidate and show the check in your notes.
An easy task's novelty must come from the MUTATION — a state key or handler
no prior task writes — never from the entity instance.

<paste output/prior_inventory/<site>.txt here — all 100 lines>
<paste output/unspent_primitives/<site>.md here>

```

Re-state these non-negotiables in each prompt, because they are the ones that
actually break downstream:

- **One app per task.** `CuaGymTaskInfo` carries exactly one `app_dir`.
- The untouched initial state must score exactly `0.0`; a correct completion
  must score exactly `1.0`.
- `reward.py` and `nemo_reward.py` must implement the *same* rubric.
- Setup and reward code must be self-contained single programs using only the
  standard library plus `requests`, must contain `__CUA_GYM_SID__` and the exact

  `/go?sid=` respectively, and the reward must print `REWARD: <float>` on every
  output path including its error path.
- Inline JSON fixtures with `json.loads(r"""...""")` — raw string, always.
- **Never gate a reward component on "the record was edited"; gate on the
  recorded value.** Several handlers write unconditionally, so a record appears
  in the diff even when nothing changed.
- Execute every `initial_setup.py` against a live throwaway sid before
  reporting done, and drive a real chromium replay at least twice from fresh
  sids. Both practices caught real bugs in batch 2 that no offline check saw.
- Benchmark rows in `webarena_benchmarks/webarena.jsonl` are **inspiration
  only**. Record `inspiration_ids` in `task.json` metadata, never in the
  user-facing instruction.
- Retrieval-shaped ideas must be rewritten as an observable writeback.

### After each batch returns

Do not trust the agent's self-report. Run the gate yourself:

```bash
python3 scripts/preflight_bundles.py output/tasks/<site> \
  --prior-batch webarena_08_18_batch_200/tasks \
  --prior-batch webarena_08_19_batch_200/tasks \
  --difficulty-split <cumulative E:M:0> --quiet
```

`--prior-batch` is repeatable and reserves all 400 prior task_ids. Then run the
near-duplicate scan **against both snapshots**:

```bash
for prior in webarena_08_18_batch_200 webarena_08_19_batch_200; do
  python3 scripts/near_dup_scan.py --new output/tasks/<site> \
    --prior $prior/tasks/<site> --threshold 0.30
done
```

Use a threshold of **0.30, not 0.45**. Batch 2's two genuine duplicates both
scored *below* 0.45; the gate threshold is too loose for thin tasks. Read every
flagged pair yourself against the four §2b tests and record the adjudication in
`PROGRESS.md`. Similarity is a triage signal, not the verdict.

Anything that fails goes back to a fresh `task-author` for that slot — do not
hand-patch 10 bundles yourself.

120 easy / 30 medium / 0 hard, and no bundle duplicates either prior batch or

`output/logs/<task_id>.jsonl` and `.stderr.log`. It is resumable.

**Note `--max-turns 220`.** The runner's default is 120, and batch 2's single
failure was an orchestrator that hit `error_max_turns` at 121 turns *after* both
of its attempts had passed — it simply died before writing `REVIEW.md`, and the
task was lost to a turn budget rather than to any defect. Do not use the default.

Add `--endpoints output/endpoints.json` if Phase 1 determined you need it.

**Budget for this honestly.** Easy tasks replay much faster than hard ones — most
are a single mutation — so per-task cost is well below batch 2's. But there are
three times as many of them, so expect the wall-clock to exceed batch 2's
regardless. At concurrency 12 with a 90-minute ceiling, 600 tasks is a long
tail measured in many hours, and Phase 2's 15 waves of authoring precede it.
Do not compensate by lowering the per-task timeout or raising concurrency past
12.

Because the run is long, the resumability matters more than it did at 200: a
task whose run directory already holds a passing `verification.json` **and** a
`REVIEW.md` containing `## Verdict: PASS` is skipped unless you pass `--force`.
If the batch process dies, restart it with the same command and it picks up
where it left off.

When the batch completes, run `scripts/detect_flaky.py` over `output/runs`. A
flaky task is **not** verified: fix its reward or replay, or replace the task.

## 7. Monitoring loop

While Phase 3 runs, poll roughly **every 5 minutes** and act on what you find.
Over a run this long, resist the urge to poll tighter — the batch moves on the
scale of minutes and 600 tasks will not finish faster for being watched.

1. Read `output/batch_status.json` — count `running` / `completed` / `failed` /
   `timeout` / `error` / `skipped`.
2. For anything not `completed`, read the tail of its
   `output/logs/<task_id>.stderr.log` and `.jsonl`.
3. Classify each failure (§8) and take the matching action.
4. Append a dated one-line summary to `output/PROGRESS.md`.

Report to the user when: a systemic failure appears (the same error across ≥3
tasks), the batch completes, or you have made a decision that changes scope.
Otherwise keep working — do not narrate every tick.

## 8. Error triage — what you may and may not fix

**Fix these yourself, immediately:**

- Missing or broken dependencies — `pip install`, `playwright install chromium`.
- A mock server that has died: restart just that tmux window
  (`tmux respawn-window -k -t cua-gym-hub:<n>`) and re-run the affected tasks.
- Endpoint resolution failures — fix `.env` or `output/endpoints.json`.
- An orchestrator that died on `error_max_turns` — re-run that task with a
  larger `--max-turns`. This is a turn-budget fix, not a weakened condition.
- Bad prompts producing consistently malformed bundles: improve the prompt and
  regenerate.
- A bad individual task: a reward that cannot discriminate the lanes, a replay
  that cannot be driven through the real UI, an ambiguous instruction, a
  mutation the mock does not support. **Delete the task and generate a
  replacement** so the site still lands at 50. Log every replacement.
- Harness scripts under `scripts/` and `cua_gym_web/`: small fixes are fine if
  the defect is genuinely there, but say so explicitly in `PROGRESS.md` and keep
  the change minimal.

**Do not do these:**

- Do not change anything under `./hub/` that affects how a mock behaves.
- Do not edit `cuagym/hub_apps.py`.
- Do not relax a reward, delete an agreement condition, or mark a task verified
  on a partial result.
- Do not raise Phase 2 authoring concurrency above 4, or Phase 3 verification
  concurrency above 12.
- Do not commit anything under `output/`.

If you hit something that would require breaking one of these rules, stop that
task, leave its artifacts in place, and report it.

## 9. Definition of done

- 600 bundles exist across the four site directories, 150 each, each site at
  **120 easy / 30 medium / 0 hard**.
- Zero duplicates of either prior batch under the §2b tests, and every pair
  flagged by the 0.30-threshold near-duplicate scan is adjudicated in writing.
- `scripts/detect_flaky.py` reports zero flaky tasks.
- Every task has a run directory under `output/runs/<task_id>/` that satisfies
  **all three** of:
  1. `REVIEW.md` contains `## Verdict: PASS`;
  2. at least one `attempt-*/verification.json` reports
     `verification.passed == true`;
  3. every attempt agrees on initial score, replay score, and verdict.

  while both of its `verification.json` files recorded `passed: false` — its

  artifacts.

  ```bash
  python3 scripts/export_nemo_rollouts.py output --output webarena_batch3.jsonl \
  ```

## 10. Inherited findings — do not rediscover any of these

`webarena_08_19_batch_200/AUTHOR_BRIEF.md` is the full list and is binding. The
four that cost the most to learn:

1. **`json.dumps` leaves bare `true`/`false`/`null` in Python source.** It
   compiles, passes static checks, then raises `NameError` at episode time.
   Gated by `js_literal_names()`.
2. **A non-raw string literal eats a JSON fixture's backslash escapes** before
   `json.loads` sees them — often silently, since `\\b` collapses to a valid
   `\b`. Always `json.loads(r"""...""")`. Gated by `broken_inline_json()`.
3. **A no-op save is a real state mutation.** Several handlers write
   unconditionally (gitlab `saveNaming` always writes `topics: []`, `NewLabel`'s
   edit branch always rewrites `updated_at`, reddit `ForumEditPage` always writes
   `tags: []`). Gate rewards on the recorded value, never on "was edited". Not
   statically checkable — this one is on you.
4. **Verify in a browser, not just offline.** Every batch-2 finding that mattered
   — a wrong iid, a star-rating label intercepting clicks, a 404 start path, a
   reward leaking credit to a form-Save — surfaced only in a real chromium replay.

Two claims in batch 2's brief were **retracted** after authors checked the
source; both are corrected in the current `AUTHOR_BRIEF.md`. Treat any
*mechanism* claim as unverified until you have read the handler yourself.
