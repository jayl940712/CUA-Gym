### The non-duplication rule

Before you write a task, and again in the mechanical gate, check it against
every bundle in `webarena_08_18_batch_200/tasks/*/*/task_instruction.json`.
A candidate is a **duplicate** — reject and replace it — if any of these hold:

1. Its `task_id` collides with a batch-1 `task_id` (or with anything already in
   the new `output/tasks/`).
2. It exercises the same *primary mutation* on the same *primary entity* as a
   batch-1 task, with only the entity instance, field value, or wording changed.
   "Rename forum X" vs "rename forum Y" is a duplicate. So is "add product Z to
   cart" vs "add product W to cart", and "hold order 000000002" vs "hold order
   000000005".
3. Its success criteria are a subset of a batch-1 task's success criteria.
   Extending a batch-1 flow with one extra trivial step does not make it new.
4. Its instruction is a paraphrase of a batch-1 instruction (same verbs, same
   nouns, reordered).

A batch-2 task **may** legitimately re-touch an entity type that batch 1 also
touched — the mocks are finite — but only when the *shape* of the work is new:
a different handler, a different multi-step composition, a cross-cutting
constraint, a lookup that determines which entity to act on, or an ordering
requirement that a batch-1 task never imposed.

### Lessons from batch 1 — inherit these, do not rediscover them

These are already-paid-for findings. Put the relevant ones in the author prompts.

- reddit `moderates()` reads only `state.moderatorOf` (`AppContext.jsx:308`),
  which is **empty** on the pristine seed. Any moderator-only route on a seeded
  forum needs `moderatorOf` injected in `initial_setup.py` or it 403s.
- reddit `ForumDeletePage` allows deletion only when
  `admin || (moderates(forum) && submissionCount == 0)`, and no seeded forum has
  zero submissions. `forums` is a single state key — setups must read the
  pristine seed from `/go`, patch it, and `set` the whole state back.
- shopping: "choose a shipping method" is not a real choice (one pre-checked
  Flat Rate row). Never assert `cart.items` after Place Order — it empties the
  cart. `submitReview` stores the star rating as a plain 1–5 Number and the
  form's "summary" field as `title`.
- shopping_admin: the category-tree Delete uses the mock's only native
  `window.confirm` (`src/pages/catalog/CategoryPage.jsx:201`); reddit message
  delete also confirms. Replay drivers must accept the dialog.
- shopping_admin `applied_at` is wall-clock — assert only "became a non-empty
  stamp", which usefully also enforces create-then-apply ordering.
- gitlab: group milestones are read-only rollups; there is no `/dashboard/labels`
  route; label delete deliberately does **not** rewrite `issues[].label_ids`
  (milestone delete does); import-project is notice-only and transfer-project
  renders `disabled`.
- Known-unsupported, already rejected — do not spend an author's time on them:
  Invite-a-group, Remove-a-group-share, Import-members, Import Tax Rates
  (needs a client-side file upload), review edit/delete, reddit user flair
  (`userFlag` has only a `(none)` option), confirm-account-deletion.
- **Systemic issue 2, now permanently gated:** `json.dumps` emits bare
  `true`/`false`/`null` into Python source. It compiles, passes static checks,
  then raises `NameError` at episode time. `scripts/preflight_bundles.py`
  carries a `js_literal_names()` AST check — keep it and keep running it.
- **Flakiness:** batch 1 shipped one flaky task
  (`shopping_wishlist_compare_direct_add_url_006`, replay 1.0×5 / 0.0×1) because
  `task_is_complete()` only requires one passing attempt. Batch 2 rewards must
  not depend on timing, ordering that the UI does not guarantee, or
  add-to-cart-by-URL races. Re-run `scripts/detect_flaky.py` at the end and
  treat any flaky task as a failed task (§9).

## 2c. Difficulty — batch 2 skews hard

Batch 1 landed at **60 easy / 99 medium / 41 hard**. That is too soft. Batch 2's
target, enforced per site:

| Difficulty | Share | Per site (of 50) | Total (of 200) |
|---|---|---|---|
| easy | 10% | 5 | 20 |
| medium | 40% | 20 | 80 |
| hard | 50% | 25 | 100 |

Within each 10-task batch that means **1 easy / 4 medium / 5 hard**. The
mechanical gate checks the mix per site (§5) — a site that comes in soft gets
its softest bundles regenerated, not relabelled.

`difficulty` is a claim about the *work*, not a free-text label. Use these
definitions and hold authors to them:

- **easy (5/site)** — one navigation plus one mutation on an entity named
  outright in the instruction. One success criterion, maybe two. No lookup, no
  ordering, no setup. This is the batch-1 median; batch 2 keeps only a few, as
  sanity-check floor tasks.
- **medium (20/site)** — 2–3 mutations, *or* one mutation gated on a lookup the
  agent must perform (find the entity matching a stated property, then act on
  it), *or* a single mutation across two pages of a form/wizard. Success has
  3+ independently-checkable criteria.
- **hard (25/site)** — must satisfy **at least two** of:
  - **≥4 distinct mutations**, or a chain where a later step depends on the
    result of an earlier one;
  - **derived target**: which entity to act on is not stated and must be
    computed from the UI (lowest-scored comment, largest pending order, the
    only product below a stock threshold, the forum with the fewest
    submissions) — with a *unique, deterministic* answer;
  - **cross-section**: the flow spans two or more distinct areas of the same
    app (e.g. create an attribute set, then a product that uses it, then a
    category that contains it);
  - **negative / exclusion constraint**: something must be true *and* something
    else must remain untouched, and the reward scores the untouched part;
  - **shortcut-defeating**: the obvious one-step approximation (rename in place,
    edit instead of create-and-retire) must score strictly less than 1.0, and
    the rubric must be shown to do so.

Hard does **not** mean long, vague, or fiddly. Every hard task still needs a
single deterministic end state, exact-value ground truth, and a replay a
browser agent can actually drive. A task that is hard because the instruction
is ambiguous is a bad task — reject it.

Partial credit matters much more at this mix: with 25 hard tasks per site, a
0/1 rubric wastes most of the signal. Every hard task must ship `components`
that pay out per completed sub-goal, summing to exactly 1.0, with the untouched
initial state still at exactly 0.0.

Record the per-task difficulty in both `task_instruction.json` and the
`task.json` metadata, and record which hard-criteria a hard task satisfies in
`task.json` metadata as `hard_criteria: [...]`.

### Batching

50 tasks from a single agent invocation produces slop. Split each site into
**5 batches of 10**, each batch given a *distinct, disjoint topic* so the 50
tasks for a site do not collapse onto the same three workflows. That is 20
batches total. Run them **4 at a time** (the Phase 2 cap; Phase 3 runs at 12).

Pick the topics yourself from what each mock actually supports — read its
`SCHEMA.md` "Observable State Changes" table and prefer rows marked ✅ (captured
in a real browser session) over ⚠ (handler-derived, unproven).

**The 20 batch-1 topic slugs in §2b are off limits**, and so are their thin
re-slices. Since batch 1 already took the broad single-area cuts, batch 2's
topics should mostly be *compositional* rather than area-shaped — organised by
the shape of the work rather than by which page it happens on. Good directions:

- **cross-area chains** — a flow that starts in one section and finishes in
  another (create a label *and* the milestone *and* the issue that uses both).
- **derived-target sweeps** — the instruction states a property, not an entity;
  the agent must find the match and act on it.
- **create-then-retire / migrate** — stand something up, move dependents onto
  it, then decommission the old one, with the rubric refusing rename-in-place.
- **audit-and-writeback** — read a computed fact out of the UI and record it
  somewhere observable (a comment, a description, a title), with the exact value
  as ground truth.
- **constraint-preserving edits** — change one thing while a named neighbour
  must stay byte-identical, and score the neighbour.
- **reversal / idempotence** — do, partially undo, and land on a specific end
  state that is not the start state (batch 1 showed pure do-then-undo is a
  no-op that cannot discriminate the lanes; ensure the end state differs).

Before locking a topic in, diff it against the site's batch-1 inventory and say
in `PROGRESS.md` in one line why it is not a re-slice.

  output/tasks/gitlab output/tasks/reddit \
  output/tasks/shopping output/tasks/shopping_admin \

Run it **in the background**. It spawns `claude --agent orchestrator` per task,

Add `--endpoints output/endpoints.json` if Phase 1 determined you need it.

A task is verified only when all of the orchestrator's agreement conditions
hold — most importantly: initial lane scores exactly `0.0`, replay lane scores
exactly `1.0`, a second run from a fresh SID also passes, and `REVIEW.md` says
`## Verdict: PASS`.

Hard tasks replay longer than easy ones, and there are 100 of them this time —
budget for a longer tail than batch 1, and do not compensate by lowering the
per-task timeout.

When the batch completes, run `scripts/detect_flaky.py` over `output/runs`.
Batch 1 shipped one flaky task because `task_is_complete()` accepts a single
passing attempt. In batch 2 a flaky task is **not** verified: fix its reward or
replay, or replace the task.

**Expect this to take many hours.** 200 tasks at concurrency 12 with a 90-minute
per-task ceiling is a long tail. That is expected; do not shorten the timeout to
make it finish faster.

## 7. Monitoring loop

While Phase 3 runs, poll roughly **every 5 minutes** and act on what you find.
Do not sit idle waiting, and do not spin at a much tighter interval — the batch
moves on the scale of minutes.

Each tick:

1. Read `output/batch_status.json` — count `running` / `completed` / `failed` /
   `timeout` / `error` / `skipped`.
2. For anything not `completed`, read the tail of its
   `output/logs/<task_id>.stderr.log` and `.jsonl`.
3. Classify each failure (§8) and take the matching action.
4. Append a dated one-line summary to `output/PROGRESS.md`. Keep it terse:
   counts, what changed, what you did.

Report to the user when: a systemic failure appears (the same error across ≥3
tasks), the batch completes, or you have made a decision that changes scope.
Otherwise keep working — do not narrate every tick.

If the batch process dies, restart it with the same command; it resumes.

## 8. Error triage — what you may and may not fix

**Fix these yourself, immediately:**

- Missing or broken dependencies — `pip install`, `playwright install chromium`,
  a missing `requirements.txt` entry for a bundle that declared one.
- A mock server that has died: restart just that tmux window
  (`tmux respawn-window -k -t cua-gym-hub:<n>`) and re-run the affected tasks.
  Restarting a server is not the same as changing it.
