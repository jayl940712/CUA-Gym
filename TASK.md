## 3. Ground rules

read-only for this task. You may read anything under it — `SCHEMA.md`,
`ROUTES.md`, `assets/task_anchors*.json`, `src/**` — and you must, to ground

Phase 2 that means 4 concurrent `task-author` agents. In Phase 3 it means
`--concurrency 4` on the batch orchestrator. Note that each orchestrator spawns
its own `reward-gen`, `golden-browser`, and `reward-audit` children — the cap of
4 applies to the top-level agents you launch, not to their descendants.

**Read the contracts before spawning anything.** In order:
`.claude/skills/webarena/SKILL.md`, `.claude/agents/task-author.md`,
`.claude/agents/web-orchestrator.md` (agent name: `orchestrator`),

## 5. Phase 2 — Generate 200 tasks

### Layout

One flat directory per site, one directory per task, so the batch orchestrator
can glob `*/task.json`:

```
output/tasks/gitlab/<task_id>/
├── task_instruction.json   # canonical human-readable contract
├── task.json               # schema-v2 manifest
├── reward.py               # offline rubric over frozen evidence
├── initial_setup.py        # NeMo setup program (omit only if setup is null)
├── nemo_reward.py          # NeMo reward program, same rubric as reward.py
├── nemo_task.json          # ready-to-inline WebArenaTaskRow payload
└── requirements.txt        # optional, only for declared popular deps
output/tasks/reddit/<task_id>/...
output/tasks/shopping/<task_id>/...
output/tasks/shopping_admin/<task_id>/...
```

`task_instruction.json` is mandatory (added in `8fddafe`, enforced by the
orchestrator's step 9) and must carry at least `task_id`, `task_instruction`,
`app_dir`, `start_path`, `difficulty`, and a `success_criteria` list of exact
observable browser-state requirements. The canonical files must all survive the
NeMo export — `nemo_task.json` inlines copies of the setup and reward code, and
must never replace, rename, truncate, or delete the originals.

Task IDs are globally unique and site-prefixed: `gitlab_*`, `reddit_*`,
`shopping_*`, `shopping_admin_*`.

### Batching

50 tasks from a single agent invocation produces slop. Split each site into
**5 batches of 10**, each batch given a *distinct, disjoint topic* so the 50
tasks for a site do not collapse onto the same three workflows. That is 20
batches total. Run them **4 at a time**.

Pick the topics yourself from what each mock actually supports — read its
`SCHEMA.md` "Observable State Changes" table and prefer rows marked ✅ (captured
in a real browser session) over ⚠ (handler-derived, unproven). Aim for breadth:
creation, editing, deletion, assignment, configuration, filtering-and-saving,
and multi-step workflows that chain two or three of those.

### Per-batch invocation

Spawn a `task-author` subagent per batch, with a prompt of this shape:

```
Generate 10 new RL tasks about <topic>.
Sites: <gitlab|reddit|shopping|shopping_admin>
Difficulty: 30% easy, 50% medium, 20% hard
Output: output/tasks/<site>/
Task ID prefix: <site>_<topic-slug>_
```

Every task-author agent must follow `.claude/agents/task-author.md` in full.
Re-state these non-negotiables in each prompt, because they are the ones that
actually break downstream:

- **One app per task.** `CuaGymTaskInfo` carries exactly one `app_dir`. Reject
  cross-site candidates rather than emitting an invalid row.
- The untouched initial state must score exactly `0.0`; a correct completion
  must score exactly `1.0`. Provide partial credit in between via `components`.
- `reward.py` and `nemo_reward.py` must implement the *same* rubric.
- Setup and reward code must be self-contained single programs using only the
  standard library plus `requests`, must contain `__CUA_GYM_SID__` and the exact
  `__CUA_GYM_WEBARENA_<APP>_URL__` placeholder from `PLACEHOLDER_MAP`, must hit
  `/post?sid=` and `/go?sid=` respectively, and the reward must print
  `REWARD: <float>` on every output path including its error path.
- If pristine hub state suffices, `initial_setup` may be `null` in the NeMo row.
- Benchmark rows in `webarena_benchmarks/webarena.jsonl` are **inspiration
  only** — sample them with `scripts/sample_webarena_inspirations.py`. Never
  copy or lightly paraphrase a benchmark question, entity combination, or
  reference answer. Record `inspiration_ids` in `task.json` metadata, never in
  the user-facing instruction.
- Retrieval-shaped ideas must be rewritten as an observable writeback.

### After each batch returns

Do not trust the agent's self-report. Run a mechanical gate over the batch:

- every bundle has all canonical files, including `task_instruction.json`
  (`initial_setup.py` may be absent only when the NeMo row's setup is null);
- `task.json` loads as `WebTaskManifest` (schema_version 2, one app, valid
  `base_url_env`);
- both episode programs `compile()`;
- `substitute()` from `cuagym/episode_code.py` resolves every placeholder
  against `hub_base_url="http://localhost"`, `base_port=8000` with nothing left
  matching `__CUA_GYM_[A-Z0-9_]+__`;
- `app_dir` is in `APP_DIRS`;
- third-party imports are limited to what `cuagym/requirements.txt` provides;
- `task_id` collides with nothing already on disk.

Write this gate once as a script (e.g. `scripts/preflight_bundles.py`) and reuse
it. Anything that fails goes back to a fresh `task-author` for that slot — do
not hand-patch 10 bundles yourself.

Phase 2 exits when 200 bundles pass the mechanical gate.

## 6. Phase 3 — Verify all 200

Use the existing batch runner; it already does concurrency, per-task logging,
resumability, and status tracking:

```bash
python3 scripts/batch_orchestrator.py \
  output/tasks/gitlab output/tasks/reddit \
  output/tasks/shopping output/tasks/shopping_admin \
  --output output/runs \
  --concurrency 4 \
  --timeout 90 \
  --dangerously-skip-permissions
```

Run it **in the background**. It spawns `claude --agent orchestrator` per task,
writes `output/batch_status.json`, and logs to `output/logs/<task_id>.jsonl`
and `output/logs/<task_id>.stderr.log`. It is resumable: a task whose run
directory already holds a passing `verification.json` **and** a `REVIEW.md`
containing `## Verdict: PASS` is skipped unless you pass `--force`.

Add `--endpoints output/endpoints.json` if Phase 1 determined you need it.

A task is verified only when all of the orchestrator's agreement conditions
hold — most importantly: initial lane scores exactly `0.0`, replay lane scores
exactly `1.0`, a second run from a fresh SID also passes, and `REVIEW.md` says
`## Verdict: PASS`.

**Expect this to take many hours.** 200 tasks at concurrency 4 with a 90-minute
per-task ceiling is a long tail. That is expected; do not shorten the timeout to
make it finish faster.

## 8. Error triage — what you may and may not fix

**Fix these yourself, immediately:**

- Missing or broken dependencies — `pip install`, `playwright install chromium`,
  a missing `requirements.txt` entry for a bundle that declared one.
- A mock server that has died: restart just that tmux window
  (`tmux respawn-window -k -t cua-gym-hub:<n>`) and re-run the affected tasks.
  Restarting a server is not the same as changing it.
- Endpoint resolution failures — fix `.env` or `output/endpoints.json`.
- Bad prompts or thin agent instructions producing consistently malformed
  bundles: improve the prompt you pass to `task-author`, and regenerate.
- A bad individual task: reward that cannot discriminate the lanes, a replay
  that cannot be driven through the real UI, an instruction that is ambiguous,
  a mutation the mock does not actually support. **Delete the task and generate
  a replacement** so the site still lands at 50 verified. Log every replacement.
- Harness scripts under `scripts/` and `cua_gym_web/`: small fixes are fine if
  the defect is genuinely there, but say so explicitly in `PROGRESS.md` and keep
  the change minimal.

**Do not do these:**

- Do not change anything under `./hub/` that affects how a mock behaves —
  components, routes, state handlers, seed data, `vite.config.js`.
- Do not edit `cuagym/hub_apps.py`.
- Do not relax a reward, delete an agreement condition, or mark a task verified
  on a partial result.
- Do not raise concurrency above 4.
- Do not commit anything under `output/` (it is gitignored for a reason).

If you hit something that would require breaking one of these rules, stop that
task, leave its artifacts in place, and report it.
